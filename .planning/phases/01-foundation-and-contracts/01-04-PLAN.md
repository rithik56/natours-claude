<objective>
Make configuration fail fast and visibly. Zod validates every Phase 1 key when the server starts. An invalid or missing key stops the process with a message naming the key, never its value. CI checks that `.env.example` lists every key and that no secret leaks into a `NEXT_PUBLIC_` name.

Purpose: Phase 1 success criterion 1 ("refuses to start with a message naming any missing or invalid config key") and D4 and S18. RESEARCH Pitfall 2 found that throwing from `register()` does not stop `next start`, so this plan uses an explicit `process.exit(1)`.
Output: the full config schema, `config-startup.ts`, `instrumentation.ts`, `.env.example`, `scripts/check-env.ts`, `scripts/smoke.ts`, the CI steps and ADR 0010.
</objective>

`src/server/config-schema.ts` (no `server-only`, no relative imports) keeps `configSchema` as a plain `z.object`, because `scripts/check-env.ts` reads its keys. The keys (A11):
- `APP_ENV`: required enum development, test, ci, staging or production.
- `APP_URL`: required http or https URL with no path, query or hash. Expose its origin.
- `MONGODB_URI`: as in plan 01-01.
- `DB_SERVER_SELECTION_TIMEOUT_MS`: as in plan 01-01.
- `SESSION_SECRET`: required, at least 32 characters (S14).
- `CORS_ORIGINS`: optional comma-separated list, trimmed, empties dropped, each entry a URL whose origin equals the entry. It parses to `string[]` and defaults to empty.
- `LOG_LEVEL`: enum fatal, error, warn, info, debug, trace or silent, default info.
- `APP_NOW`: optional ISO date or datetime used by the clock (QA-20).

`parseConfig(env)` treats empty strings as missing, then applies the cross-field rules with `superRefine`:
- APP_URL must be https when APP_ENV is staging or production;
- APP_NOW is allowed only in development, test or ci.
Give every key an explicit developer-facing message ("is required", "must be at least 32 characters", "must be an https origin in staging and production"). These messages go to developers on stderr, never to users. Messages never interpolate the received value.

`src/server/config.ts` keeps `getConfig()` lazy and memoised, and returns the parsed config plus the derived fields `appOrigin` (string), `corsOrigins` (string[]) and `isProductionLike` (true for staging and production).

`src/server/config-startup.ts` starts with `import 'server-only'` and exports `loadConfigOrExit(): void`. It calls `getConfig()`. On a ZodError it writes `Invalid configuration:` followed by one line per issue, `  - KEY: message` in schema order, to `process.stderr`, then calls `process.exit(1)`. It never writes a value and never uses console (no-console is an error). Any other error is rethrown.

`src/instrumentation.ts` exports `async function register()`, which returns early unless `process.env.NEXT_RUNTIME === 'nodejs'`, then dynamically imports `./server/config-startup` and calls `loadConfigOrExit()`. This NEXT_RUNTIME read is one of the documented `process.env` exceptions (ARC-26, ADR 0010).

Fallback: if the Task 2 smoke run shows that `next start` fails to load the instrumentation hook because `server-only` throws in that layer, do three things:
- make `config-startup.ts` call `parseConfig(process.env)` directly, without importing `config.ts` or `server-only`;
- add it to the R6 exemption list in `scripts/check-conventions.ts`;
- record this in ADR 0010.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| environment to server | deploy-time environment values become runtime config |
| repository to public | `.env.example` is committed to a public repository |
| server to browser bundle | any NEXT_PUBLIC_ value is inlined into client JavaScript |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-11 | Information disclosure | config-startup.ts | high | mitigate | Error output names keys and fixed messages only; the test asserts no env value appears in stderr |
| T-01-12 | Spoofing | SESSION_SECRET | high | mitigate | Minimum 32 characters checked at startup (S14); boundary test 31 and 32 |
| T-01-13 | Information disclosure | NEXT_PUBLIC_ variables | high | mitigate | check-env rejects SECRET, KEY and PASSWORD in NEXT_PUBLIC_ names in CI (S18) |
| T-01-14 | Elevation of privilege | APP_ENV | high | mitigate | APP_ENV required with no default, so production can't fall back to development fakes |
| T-01-15 | Spoofing | public origin | medium | mitigate | APP_URL config is the only origin source (SEC-12); https enforced in staging and production |
| T-01-SC | Tampering | npm installs | high | mitigate | No new packages in this plan |
