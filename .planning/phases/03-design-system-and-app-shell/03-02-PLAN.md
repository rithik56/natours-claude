  <behavior>
    - At desktop widths (≥64em) the full nav (Tours, My tours, Log in/Sign up or Account) is always visible, no menu button.
    - At mobile widths (<64em) a menu button with `aria-expanded="false"` is shown; clicking it sets `aria-expanded="true"` and reveals the nav as a plain list; clicking again (or re-clicking the button) collapses it.
    - With JavaScript disabled, the nav list renders unconditionally (not hidden behind a script-only toggle) — CSS alone may visually collapse it behind a `<details>`/checkbox-free disclosure only if that disclosure itself needs no script; since the brief calls for a scripted `aria-expanded` toggle (U19), the safe no-JS fallback is: the button is a plain, non-interactive label and the nav list is always present in the DOM and visible by default when JavaScript hasn't hydrated (mobile-first CSS shows the list; the Client Component's `useState` only adds the collapse behavior once hydrated).
  </behavior>
  <action>
Build `ui/mobile-menu.tsx` as the first Client Component in the project: start the file with `'use client' // client: needs onClick and open/closed React state for the mobile nav disclosure (R1)`, per `scripts/check-client-boundaries.ts`'s required shape. Props: `{ links: ReactNode }` (receives the already-built nav links as children so `mobile-menu.tsx` owns only open/closed state, not link content/auth logic — keeps it a pure presentational wrapper per DEL-12's `ui/` boundary). `useState` for `isOpen`; a `<button aria-expanded={isOpen} aria-controls="site-nav" onClick={...}>` with a hamburger glyph/label; the nav itself always renders in the DOM (`<nav id="site-nav" aria-label="Main">{links}</nav>`), visibility controlled by a CSS class driven by `isOpen` at mobile widths only — at desktop widths CSS always shows it regardless of `isOpen` (U19's "without JavaScript, the links are shown in a plain list" is satisfied because the nav exists in the DOM unconditionally; the button is the only thing JavaScript adds visually).
