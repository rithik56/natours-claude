## Phase Goal

ROADMAP Phase 4 goal, quoted verbatim (not in user-story form; no story is invented): A traveller can find a tour that fits their fitness, dates and budget, and see its route, itinerary, guides, reviews and photo credits. API clients get the same catalogue.

<objective>
Admin tour writes over JSON (D-12, the last slice before images): PATCH, POST and DELETE on /api/v1/tours with strict schemas, load-set-save updates, the bookings 409 rule, review clean-up and exact cache invalidation. The cover becomes optional (D-13) and cover-less tours stay out of the public catalogue; the access rule follows F6 as written (D-16).

Purpose: admins and lead guides can manage the catalogue through the API without ever corrupting ratings, slugs or images, and visitors never see an incomplete tour.
Output: POST, PATCH and DELETE handlers, `tourCreateSchema` and `tourUpdateSchema`, `createTour`, `updateTour`, `deleteTour`, `countForTour`, `deleteForTour`, ADRs 0036 and 0037.
</objective>

<assumption_delta_decision>
- Noun: tour cover image (`imageCover`).
- Decision: no-change to the identity model. D-13 makes the field optional, but the cover stays the single cover of the tour; a cover-less tour is a draft the public read path filters out, not a second kind of tour, and adding a cover through the images endpoint (plan 04-13) completes it.
- Rationale: the user settled D-13 on 2026-11-16; an add-alongside model (a separate draft type) is not in play, and every public read already goes through the cached catalogue, where one filter excludes cover-less tours.
</assumption_delta_decision>

<decisions>
- **D-13 (settled by the user):** `imageCover` optional; catalogue and every public read skip cover-less tours; GET /api/v1/tours/[id] returns them with `imageCover: null`. Reversibility: costly (the model and public filter), already settled, so no new checkpoint.
- **D-16 (settled by the user, SEC-24):** lead guides and admins may manage any tour, including price and deletion. Reversibility: reversible (one access declaration per route).
- **Delete order without a transaction** (RESEARCH A11: the standalone test server has no transactions): check bookings, delete the tour, delete its reviews, delete stored photos best effort, then clear tags.
- **Duplicate name gets the approved specific message**: the service turns the duplicate-key error on `name` or `slug` into `AppError('CONFLICT', messages.tours.duplicateName)`.
</decisions>

<assumptions>
- [edge F6 concurrency, flagged] A booking created between the bookings count and the tour delete would leave a booking for a deleted tour. Phase 4 creates no bookings; Phase 6's checkout checks the tour exists. Accepted for Phase 4, recorded in ADR 0036's consequences for Phase 6.
</assumptions>
