ROADMAP Phase 4 goal, quoted verbatim (not in user-story form; no story is invented): A traveller can find a tour that fits their fitness, dates and budget, and see its route, itinerary, guides, reviews and photo credits. API clients get the same catalogue.

<objective>
Give the tour page its own JavaScript budget, including the lazily loaded Leaflet map (R9 as amended, ADR 0018), and apply the user's boundary-simplification choice from plan 04-08.

Purpose: Leaflet loads only on scroll, so Lighthouse never sees it; without a separate check the map's cost could grow unnoticed. The `/` budget stays exactly as Phase 1 set it.
Output: route-list budgets in `docs/bundle-baseline.json`, `lighthouserc.cjs` and `measure-bundle.ts`; the final boundary file.
</objective>

<decisions>
- **The tour route's floor is the framework floor recorded for `/` in Phase 1 (138,107 bytes)**, because R9 measures each page against the Phase 0 framework baseline and the tour page did not exist then; recording a fresh floor would hide 40 KB of growth. Reversibility: reversible.
- **Lazy allowance 51,200 bytes (50 KB)**: Leaflet 1.9.4 measured 42,661 bytes gzipped JavaScript plus 3,558 bytes CSS (RESEARCH), plus room for the map component itself. Checked from the production build output, not by Lighthouse. Reversibility: reversible.
- **The lazy check identifies the map's chunks by the marker string `leaflet-container`**, present in Leaflet's JavaScript and CSS. Reversibility: reversible.
</decisions>

<assumptions>
- The production build emits Leaflet into chunks separate from the tour page's eager chunks (verified for Turbopack in RESEARCH Pattern 8); if a build ever inlines the marker into an eager chunk, the eager Lighthouse budget would catch the growth anyway.
</assumptions>
